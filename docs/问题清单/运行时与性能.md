## 一、本次新增问题（用户实测反馈）

### ① 行情历史数据深度严重不足（"只有一年 / 不完整"）

**现象**：行情页、回测/选股/因子的历史窗口都很短，无法获取多年"完整"数据。

**代码证据（全链路把历史窗口压死）**
- 行情主页面 `frontend/src/views/QuoteView.vue:44` 调 `/kline` 时写死 `days: 90` —— 默认行情图仅展示**最近 90 天（≈4 个月）**，连一年都不到。
- 研究类 UI 人为封顶：`frontend/src/views/BacktestView.vue:301` 与 `FactorRegressionView.vue:103` 的"历史长度(日)"输入框均为 `min="60" max="360"` —— **最多只能选 360 天（≈1.5 年）**。
- 后端默认也偏短：`backend/app/routers/quote.py:28` `get_kline(code, days: int = 150)`；`backend/app/routers/selection.py:107` `_fetch_technical_values(..., hist: int = 260)`；`frontend/src/views/MLView.vue:16` 默认 `hist=240`。
- 底层适配器再砍一刀：`backend/app/adapters.py:468` 新浪日K `datalen={max(1, min(days, 1023))}`；`adapters.py:495` 东财日K `lmt={max(1, min(days, 500))}` —— **单次回源长度被硬封顶 500/1023 天**，即便前端想拉长也会被静默截断。

**影响**：做长周期回测、跨牛熊验证、年线/多年因子时数据不足；行情页看不到长期走势；所谓"完整数据"在现有代码路径下根本拉不到。

**建议方向（不修改）**：前端放开 `hist` 上限（如 2500/5000）、默认 `days` 提到 250+；`adapters` 放开新浪 1023 / 东财 500 的单笔封顶（或分页累计长历史）；`quote` 默认 `days` 提高到 250；结合已落库的 `kline_cache` 做"按需回源补齐长历史"。

### ② 频繁 timeout 警告 / 运行十分缓慢

**现象**：点选股、回测、ML 训练、行情加载时经常弹 timeout，整体很慢。

**代码证据（根因按重要性排序）**

1. **HTTP 连接不复用（最关键性能根因）** — `backend/app/adapters.py:26-39` 的 `_http_get` **每次调用都新建 `httpx.AsyncClient`**（且位于重试循环内，失败时最多新建 3 个），无连接池、无 TCP/TLS 复用。`_fetch_sina_market` 同理（`adapters.py:388` 每次重建 client）。选股/回测/ML 数据集要对成百上千只股票各发一次 kline 请求，握手开销被成倍放大，这是"十分缓慢"的主因。

2. **前端 60s 超时过短 + 后端同步阻塞** — `frontend/src/api/client.js:9` 普通请求 `timeout: 60000`（仅长任务放宽为 5min）。而大量操作在 60s 内跑不完 → 前端直接弹 timeout 警告。

3. **K 线并发上限偏低** — `backend/app/routers/selection.py:110` `_fetch_technical_values` 用 `asyncio.Semaphore(15)`，单股 kline 是一次第三方网络往返（timeout 10s）。当 `poolSize` 为 500/1000/3000 时，15 并发下要分 30+/67+/200+ 批，总耗时极易超 60s。

4. **候选池/板块构建偏慢** — `backend/app/adapters.py:384-408` `_fetch_sina_market` 对大 `limit` 分页到 `_SINA_MAX_PAGES=50`、每批 5 并发；`sector:` 分支更会先拉 3000 只全市场再本地过滤（line 348）。单 page 网络 timeout 15s，整体偏慢。

5. **强依赖第三方实时接口、无预热缓存** — 历史/行情全部现拉；网络抖动时单笔 10–15s 超时后还要重试（指数退避），进一步拖慢并可能撞上 60s 上限。`fetch_market_list` 虽有 60s 内存缓存（`MARKET_CACHE_TTL`），但 TTL 短、空结果不缓存。

6. **匿名限流易撞 429** — `backend/app/main.py:41` 匿名 `60 次/分钟`。未登录或多标签页下，行情页逐只拉 quote+kline 很容易触发限流，表现为"卡/慢/偶发失败"。

7. **与第一批盯盘 bug 互相干扰** — 第一批已确认的调度 bug（默认不启动 / 重启丢失 / 交易日误判）若存在，信号与净值不更新，用户也可能误判为"行情不动 = 慢"。

**影响**：大池下的选股/回测/ML 训练频繁超时失败，基础交互也偏卡，整体体感"十分缓慢"。

**建议方向（不修改）**
- `_http_get` 改为**模块级共享 `AsyncClient`**（连接池复用），这是性价比最高的单点改法。
- 提高 kline/quote 并发上限（`Semaphore(15)` → 更高或按池大小自适应）；大池操作改走已有的 `jobs` 后台任务 + 前端轮询，避免 60s 同步阻塞。
- 第三方单笔 `timeout` 下调到 5–8s 并快速失败；`market_list` 缓存更激进 + 启动预取。
- 前端普通请求 `timeout` 放宽或默认走 `longTask`；限流阈值对登录用户更宽松（已有 `_USER_LIMIT=600`，但需登录才生效）。
