## 一、概要

平台覆盖选股、分层回测、事件驱动回测、分钟回测、表达式因子、机器学习（GBDT/LightGBM）、组合优化、Barra 风格风险归因、盯盘调度等功能。经对全部核心模块的逐文件审查，确认存在 **5 大类问题**，其中「盯盘调度无法使用」为明确的功能性 bug（含多条根因），其余为能力缺失与设计缺陷。

## 二、问题清单（按诉求分类）

### ① 因子与数据数量过少（缺期货 / 期权 / ETF / 指数 / 行业 / 宏观）

**诉求**：用户期望接入期货、期权等多品种数据，当前完全不具备。

**代码证据**
- `backend/app/adapters.py:179-186` — `BOARD_MATCHERS` 仅含 A 股板块：`all / sh_main / sz_main / gem / star / bse`，**无任何期货/期权/ETF/指数（除基准）分类**。
- `adapters.py` 全仓搜索无 `fetch_future` / `fetch_option` 等函数；数据源仅为腾讯/新浪/东财 A 股行情（`fetch_kline`、`fetch_quotes`、`fetch_market_list`）。
- `backend/app/factors.py` 因子库 = `FACTORS`（约 24 个技术量价）+ `SNAPSHOT_FACTORS`（约 18 个财务/资金流/北向），**无期货/期权因子、无行业因子、无宏观因子**。

**影响**：平台只能做 A 股现货的有限量化研究，无法覆盖衍生品、跨资产与多因子（行业/风格/宏观）研究，与"量化研究平台"定位差距明显。

**建议方向（不修改）**：扩展 `adapters.py` 数据源适配器（期货/期权行情、合约表）；在 `factors.py` 增加衍生品/行业/宏观因子；在 `BOARD_MATCHERS` 与板块枚举中开放相应品种。

---

### ② 历史时间区间与板块 / 个股不可自选

**诉求**：应能在选股时自选时间段、股票类型（板块），并直接指定个股集合。

**代码证据**
- `backend/app/routers/selection.py:89-90` — `SelectBody` 仅有 `board: str = "all"`，**无 `startDate`/`endDate` 字段**；`run_select`（line 119）也未接收时间区间。
- 同文件 `BacktestBody`（line 250-264）却带有 `startDate`/`endDate` —— **回测支持时间区间，而选股不支持**，同类能力在模块间不一致。
- `backend/app/routers/strategies.py:96-97` — 用户自定义因子仅 `composite`（加权组合）类型，选股标的来自板块/行情榜，**没有"直接传个股列表作为选股池"的参数**。
- 盯盘扫描 `_scan_signals`（`scheduler.py:141`）标的范围 = `watchlist` 表，需用户先手工添加个股，无法按条件批量筛选个股进入监控。

**影响**：无法执行"在 2023-01 至 2024-12 区间内筛选某板块"这类最常见研究动作，研究灵活度严重受限。

**建议方向（不修改）**：在 `SelectBody`/`run_select` 增加 `startDate`/`endDate`；新增"自选个股池"参数（直接传 code 列表）；板块枚举扩展后开放期货/期权/ETF 品种选择。

---

### ③ 模型系数不可主观调整、不能自建模型、模块间共享不足

**诉求**：模型跑出后应能让操作者主观调整系数（含机器学习），或让操作者自己搭建模型，并将模型在模块间共享做回测/模拟盘。

**代码证据**
- 机器学习链路 `backend/app/routers/ml.py` 仅 `evaluate / train / optimize / score / ml_backtest / models`。`optimize`（line 77）为 Optuna **自动**寻参，**无任何让人工调整模型系数/权重/阈值的入口**。
- `backend/app/ml.py` 训练后超参固化；`build_dataset` 默认 `use_snapshot=False`（只用技术因子），无 UI 让用户对模型输出做人工加权/调权。
- 自定义模型搭建受限：`backend/app/routers/strategies.py:96-97` user_factors **仅支持 `composite`**，不支持让用户"自己搭建一个模型/策略"。
- 模块间共享断裂：`VALID_KINDS = ("select","backtest","regression","intraday")`（`strategies.py:13`）**不含 `ml`/模型类型**，即 ML 训练出的模型**无法保存为 saved_strategy 在策略中心一键重跑，也无法直接接入模拟盘/回测**。
- ML 模型回测走独立 `ml_backtest`（`ml.py:140`），与选股回测 `run_backtest` 是两套路径，结果与模型不互通。

**影响**：研究者无法在 ML 模型产出后做人工干预（调权重、设阈值、组合多模型），也无法把自建模型沉淀为可在回测/模拟盘中复用的资产——"研究 → 模拟"闭环断在最后一步。

**建议方向（不修改）**：ML 产出后暴露系数/权重/阈值的只读可视化 + 人工覆盖接口；放开 user_factors 支持"自定义模型"类型；将 ML 模型纳入 `saved_strategies` 与 `VALID_KINDS`，打通"模型 → 回测/模拟盘"共享链路。

### ④ 盯盘调度功能无法使用（功能性 bug）

**现象**：用户反馈"盯盘调度功能依旧无法使用"。经代码审查，存在多条导致该模块实际不工作的根因：

**Bug A — 调度器默认不启动，且未在应用启动时拉起（核心根因）**
- `backend/app/main.py:99-102` — `on_startup` **仅调用 `db.init_db()`，没有 `scheduler.start()`**。
- `backend/app/scheduler.py:21` — `_enabled = False`（默认关闭）；调度器只有在收到 `POST /monitor/toggle` 时（`scheduler.start()`，line 47-55）才创建并启动 `AsyncIOScheduler`。
- 后果：服务端重启后调度器处于"未启动"状态；若前端未显式点击开启且接口调用成功，15:05/15:10 的定时任务**永远不会执行**。用户很可能误以为"开了但还是没反应"，实际是根本没拉起。

**Bug B — 调度器为纯内存态，重启即丢失**
- `scheduler.py` 的 `_scheduler / _enabled / _last_run / _last_signals` 均为模块级全局变量（line 20-23），**不随进程持久化**。
- 虽有 `scheduler_runs` 表落盘运行记录，但 `_enabled` 与定时器本身不持久，进程重启必须重新 toggle。

**Bug C — 交易日判断依赖网络，节假日/调休不可靠**
- `_is_trading_day()`（`scheduler.py:91-99`）先排除周末，再用 `adapters.fetch_kline("sh000001",400)` 推断交易日（line 79）。
- 网络失败退化为"非周末即交易日"（line 98），且 `day_of_week="mon-fri"` 固定（line 52-53）。**无本地交易日历**：调休上班的周末会误触发，节假日过滤依赖网络、不可靠。

**Bug D — 前端文案与后端逻辑不一致（误导用户）**
- `backend/app/scheduler.py:146` 注释明确"取消旧版 codes[:20] 硬截断：全量扫描"，但 `frontend/src/views/MonitorView.vue` 标题仍写"盯盘信号（watchlist 前20）"，且 `warn-box` 文案"节假日未做日历过滤，仅排除周末"——前端显示与后端实际行为/已知限制描述脱节，用户难以判断真实状态。

**影响**：盯盘（自动刷新净值 + 生成信号）在默认部署下基本处于"假死"状态，需手动触发且重启失效，交易日判断还不严谨。

**建议方向（不修改）**：在 `on_startup` 中按配置自动 `scheduler.start()`；将 `_enabled` 持久化到配置表、启动时恢复；引入本地交易日历；对齐前端文案。

### ⑤ 其他发现的问题

1. **JWT 密钥重启失效** — `backend/app/auth.py` 中 `QUANT_JWT_SECRET` 未配置时随机生成，进程重启后所有已签发 token 失效，需重新登录。
2. **风险归因风格因子过少** — `backend/app/risk.py` `build_style_panel` 风格因子仅 `[momentum, volatility, turnover, ep, bp]` 5 个，远不足以做 Barra 级归因。
3. **分钟回测仅支持单股** — `backend/app/intraday.py` 为单标的分钟回测，无组合级分钟回测。
4. **选股默认不融合财务快照** — `ml.build_dataset` 默认 `use_snapshot=False`，快照类因子（财务/资金流）在多数研究路径中实际未被使用，因子库相当部分"闲置"。
5. **限流/CORS 强依赖环境变量** — `main.py` 限流阈值、CORS 白名单走环境变量，部署文档缺失时易踩"连不上/被限流"。
6. **数据源无降级/容灾** — `adapters.py` 全部走第三方实时接口，无离线/多源容灾，网络抖动时交易日判断、扫描、选股均受影响。
7. **基准不可配置** — 基准代码硬编码（如 `sh000001`），回测 benchmark 不可选。
8. **历史报告已存在** — 项目根目录已有 `TEST-main_代码审查报告.md`、`TEST-main新版优化空间审计报告.md`、`TEST-main程序Bug清单与竞品对比分析.md`、`功能运行报告.md`、`量化平台改进建议书.html`。本报告为针对本次 5 点诉求的增量问题清单，结论角度互补。
