## 一、创建模型后的「调参」功能出现 network error（重点）

### 1.1 现象
在 `MLView`「已训练模型」表中点「调参」按钮（打开人工调参面板），或保存调参配置时，前端弹出 **network error**，调参面板打不开 / 配置保存失败，调参功能无法使用。
> 注：本文档「调参」指 `MLView.vue` 的**人工调参面板**（特征权重 + 阈值），即用户最初诉求「模型跑出来之后主观调整系数」。

### 1.2 前端调用链路（文件:行）
- 打开面板：`MLView.vue:54-64` 的 `openAdjust(m)` → `api.get('/ml/models/${m.id}/params')`（line 60）
- 保存配置：`MLView.vue:77-83` 的 `saveAdjust(m)` → `api.post('/ml/models/${m.id}/adjust', { ...adjustPayload(), saveArtifact: true })`（line 79）
- 错误表现：`client.js:39` 判定 `isNetwork = !err.response`，**只有"请求完全无 HTTP 响应"（连接被重置 / 后端崩溃 / 超时未响应）才会弹 network error** 并带「重试」。

### 1.3 根因 A（主因）：`load_model_meta` 无条件反序列化整包模型，对版本敏感、且为同步阻塞
- `routers/ml.py:168-174` `get_model_params` 是普通 `def`（不经 jobs 异步），内部调 `ml.load_model_meta(mid)`。
- `ml.py:538-572` `load_model_meta`：即便已存在 `.json` 侧车文件，仍 **无条件执行 `bundle = joblib.load(path)`（ml.py:553）** 以读取 `feature_names` 与 `feature_importances_`。
  - 这会把**整个训练好的模型包（含 GBDT/LightGBM booster）从磁盘反序列化进内存**，属于 CPU/IO 密集操作，且**对 `lightgbm` 版本高度敏感**。
  - 若模型保存时的 `lightgbm` 版本与当前运行环境不一致，`joblib.load` 反序列化原生扩展对象时会触发 **段错误（segfault）/ 原生崩溃**，导致 **uvicorn 单 worker 直接死掉** → 之后的所有 HTTP 请求连接被重置 → 前端收到「无响应」→ 弹 **network error**。
  - 这恰好命中 `client.js:39` 的 `isNetwork` 判定（没有 HTTP 响应），与用户观察到的现象一致。
- 该端点为普通 `def`（`routers/ml.py:169`），在单 worker + 本文档后续「无连接池/慢」背景下，反序列化重模型还可能挤占事件循环、慢到超过前端 5 分钟超时（即便超时也是「无响应」→ network error）。

### 1.4 根因 B（次级路径）：Optuna 调参与寻优同步执行、未走 jobs 队列，易超 5 分钟
- `routers/ml.py:86-108` `/ml/optimize`（ML 超参寻优）与 `OptimizeView.vue:54-63` 调用的 `/optimize/backtest`（因子/模型参数寻优）**均为同步执行，未提交到 `/api/jobs` 异步队列**。
- 路由注释已自承「大数据集建议走 /api/jobs（kind=ml-optimize）」（routers/ml.py:92）。`nTrials=30` 在大候选池下常 > 5 分钟 → 前端 `api` 默认 `timeout: 300000`（client.js:9）到点 → 无响应 → network error（呼应《运行时与性能》篇 timeout 问题）。
- 若用户把 `OptimizeView` 的「开始寻优」也理解为"调参"，这条路径同样会报 network error。

### 1.5 根因 C（概念性缺陷）：对树模型「调参」并不等于「调整系数」
- 即便调参接口正常返回，「人工调参」的实现只是：
  - `_apply_feature_weights`（`ml.py:707-720`）：对**输入特征向量做线性缩放**（乘权重）；
  - `_apply_threshold`（`ml.py:723-727`）：预测分整体平移（单调变换，**不改变排序**）。
- 对于 **GBDT / LightGBM 树模型**，重新缩放输入特征并不会改变模型**内部训练好的系数/分裂规则**，只是轻微改变输入分布 → 分裂路径微调 → 预测排序变化有限。即用户最初诉求「主观调整系数包括机器学习也是」，**只对 manual/线性模型真正满足，对树模型名不副实**。
- 这解释了用户「依旧无法实现」的体感：面板即使能打开，调出来的"系数"对树模型也达不到"调整模型本身"的预期效果。

### 1.6 修复方向（仅列出，未改代码）
- **A**：`load_model_meta` 改为**懒加载 / 只从 `.json` 侧车读 meta**，特征重要性在训练时即写入 `.json`，避免每次"调参"都 `joblib.load` 整包；模型反序列化失败时返回结构化 422/500（有 HTTP 响应）而非崩溃 worker。
- **A**：部署锁定 `lightgbm` 版本（写进 `requirements.txt` 或用虚拟环境），消除跨版本反序列化段错误风险。
- **A**：uvicorn 改用多 worker（`--workers N`）或把 `params` 接口挂到 jobs 异步，单点崩溃不拖垮全站。
- **B**：`/ml/optimize`、`/optimize/backtest` 默认走 `/api/jobs` 异步，前端轮询进度，避免同步 5 分钟超时。
- **C**：对树模型提供"重训练时注入人工先验/约束"或"可解释系数视图"，让"调参"语义名副其实。

## 二、板块不支持多选（只能单选）

### 2.1 现象
行情 / 选股 / 回测 / ML / 寻优等所有页面的「板块」下拉，只能选**一个**板块，无法组合（如"沪市主板 + 创业板"）。

### 2.2 根因：前后端均为单一 board 值，无多板块路径
- **前端**：全项目 grep `multiple` / `el-select` / `type="multiple"` **零匹配**（无任何多选控件）；所有板块选择均为 `<select v-model="board">` 普通单选，例如：
  - `MLView.vue:312-323` `<select v-model="board">`（选项 all/sh_main/sz_main/gem/star/bse）
  - `OptimizeView.vue:124-131` `<select v-model="board">`
  - `SelectView.vue` / `BacktestView.vue` 同理（board 为单个 ref）。
- **后端**：所有相关请求体的 `board` 字段均为**单个 `str`**：
  - `SelectBody.board: str = "all"`（selection.py:91）
  - `BacktestBody.board: str = "all"`（selection.py:349）
  - `EvalBody.board: str`（routers/ml.py:13）、`OptimizeMlBody.board: str`（routers/ml.py:72）
  - ML/回测打分 `ScoreBody.board: str`（routers/ml.py:225）、`MLBacktestBody.board: str`（routers/ml.py:266）
- **适配器**：`fetch_market_list(board, ...)` 按单个 `BOARD_MATCHERS` 键解析谓词过滤候选池（`adapters.py:208-219`），**没有任何 union 多个板块的代码路径**。

### 2.3 关联隐藏 bug：同叫"沪深300/中证500/ETF"，不同模块行为不一致
- `BOARD_LABELS`（selection.py:26-28）向用户提供了 `hs300 / zz500 / etf` 选项；`BOARD_MATCHERS`（adapters.py:216-218）也定义了它们，但 `hs300`/`zz500` 的 matcher 是 **`lambda c: True`（即全市场）**，注释写明"需从成分表过滤"。
- 后果：
  - **选股** `run_select` 对 `hs300/zz500` 走 `fetch_index_constituents`（selection.py:200-205）→ **真实成分股过滤**；
  - **回测** `run_backtest`（selection.py:411）与 **ML 打分/回测**（走 `fetch_market_list`）用通用 matcher → `hs300/zz500` = 全市场，**并没有过滤成成分股**。
  - 即同一"沪深300"在选股 vs 回测/ML 中含义不同，单选下就已有正确性问题，多选缺失只是雪上加霜。
- 另：早期版本 `BOARD_MATCHERS` 仅有 6 项（all/sh_main/sz_main/gem/star/bse），与 `BOARD_LABELS` 的 9 项不一致，说明板块清单前后端长期未对齐。

### 2.4 修复方向（仅列出，未改代码）
- 将 `board` 改为 `list[str]`（或 `boards`），前端改用多选组件（如 `el-select multiple` 或复选组）；
- 后端 `fetch_market_list` 支持多板块谓词 **OR 合并**，并对 `hs300/zz500` 统一走 `fetch_index_constituents` 真实成分过滤，消除跨模块行为不一致；
- 对齐 `BOARD_LABELS` 与 `BOARD_MATCHERS`，去掉"挂名"却不过滤的选项。

## 三、与既有诊断的交叉关联（简要）
- **板块单选 + 历史被压（第二篇）** → 样本空间同时受"板块不可组合"与"历史 ≤1023 天"双重限制，策略可测试域很窄。
- **调参 network error（本文 A/B）+ 无连接池/单 worker（第二篇）** → 互相放大：一次重模型反序列化或长时 Optuna 同步计算，足以拖垮全站并触发 network error。
- **调参面板存在但坏掉（本文）** → 修正第一篇 ③ 的判断：后端其实已实现"人工调参 + 模块间共享（打分/回测/盯盘可传 adjustId）"（routers/ml.py:177-220、MLView.vue:160-162/175-179），但**因 network error bug 实际不可用**，且对树模型的"调参"语义仍不达预期。
