# 应用排查：机器学习时间长度过长跑不出结果

> 诊断日期：2026-08-18
> 范围：ML 训练 / 评估 / 回测（FastAPI + Vue3 前端，MLView 页）
> 性质：静态代码诊断，未改动任何文件

## 1. 现象复述

用户在 ML 页把"时间长度"设得较大（历史长度 `hist` 偏大，或 `startDate~endDate` 时间段跨度偏大）后，
机器学习任务**跑不出结果**。体感分两种：

- **直接报错**：后端返回「有效样本不足，无法构建数据集」之类提示，任务失败。
- **一直转圈 / 无响应**：前端持续等待，长时间拿不到结果（进度轮询无进展）。

两种体感对应两条不同的代码路径，均与时间长度过大直接相关。

## 2. 关键参数说明

ML 任务的时间维度由两部分决定：

- **历史长度 `hist`**（训练/评估界面上的"时间长度"类参数，默认约 1024 天）：
  决定每只股票要拉取多少天的日 K 线，以及由此生成的训练样本行数。
- **时间段 `startDate ~ endDate`**（分时段训练 / 验证区间）：
  限定样本落在哪个日期区间。

无论用户调的是 `hist` 还是时间段，本质都等价于**"让每只股票拉取的 K 线天数变长"**。

## 3. 根因分析

### A. 数据抓取层（最直接、几乎必现）

- 当时间长度超过约 **1500 天**后，数据源从新浪/腾讯切换到东财**分页拉取**，分页页数随天数近似线性增加
  （每页约 1000 天，要发多轮 HTTP 请求）。
- 超长窗口 + 多股票并发拉取时，极易触发上游**限流 / 超时**；更关键的是：
  抓取失败在代码里是**静默跳过该股票**（计入失败计数后 `continue`），不会中断整体流程。
- 当**整池股票**的 K 线都拉取失败时，最终没有可用样本 → 后端直接抛
  「有效样本不足，无法构建数据集」——这就是用户看到的"跑不出来结果（报错）"。

> 佐证：验证操作手册已实测，`hist=1023、候选池=30` 时曾出现"候选池 30 只，K线≥40 日的仅 3 只"，
> 即 27 只的并发 K 线请求整体失败/超时被静默丢弃。说明即便在默认 1024 附近、多股票并发拉 K 线就已不稳，
> 时间长度再拉长只会更差。

### B. 计算层（慢到跑不完 / 阻塞）

- 每只股票 K 线越长，生成的训练样本行数越多（样本数 ≈ 候选池大小 × 单票 K 线长度）。
- 时间长度越大 → 单票样本越多 → 单次 LightGBM 训练成本按样本量线性上升。
- 若叠加：
  - **超参寻优**（默认约 30 次 trial，每次 trial 内都重训一个模型），总成本 ≈ 30 × 单次训练；
  - **ML 回测**：用**已落盘模型**逐调仓日对全池打分（不重训模型，只预测），调仓日数 ≈ 历史长度 / 调仓间隔
    （已自适应步长封顶 200 个调仓日）。历史越长、池越大、步长越密，逐日截面打分耗时近似线性膨胀；
  - **Walk-Forward CV（评估）**：按 `n_splits`（默认 5）折各重训一个模型，重训次数 = 折数，而非调仓日数。
- 当单次任务耗时远超后端耐心或耗尽单 worker 资源时，体感即"一直转圈 / 跑不出来"。
- 特别注意（诊断时状态）：**ML 回测（ml-backtest）的逐调仓日打分循环直接在事件循环里执行、未丢到线程池**，
  长时间任务会阻塞整个后端进程，连进度轮询接口都响应不了 → 前端无限转圈。
  （该问题已随 2026-08-18 修复落地：打分循环已移入 `run_in_executor`，见《../优化建议/应用优化建议_机器学习时间长度过长_20260818.md》。）

### C. 隐藏放大机制（时间段过长）

- 若用户填了 `startDate / endDate` 且跨度过大，后端会**自动把 `hist` 抬升**到
  "时间段跨度 + 约 300 天"（覆盖因子回看窗口），即使你没有手动调大 `hist`。
- 也就是说：**只拉大时间段，也会触发 A、B 两类问题**，且用户往往意识不到自己的 `hist` 已被悄悄撑大。

## 4. 前端超时影响（次要）

- ML 训练 / 评估走 jobs 异步 + 前端轮询，提交本身是异步短请求，不会因前端 5 分钟超时直接中断。
- 真正卡住的是**后端任务执行本身**（数据抓取超时 + 计算膨胀），而非前端超时。
- 唯一例外是 ML 回测的"阻塞事件循环"问题（见 B 末），会让轮询接口也卡死。

## 5. 修复方向（仅列方向，未实施）

1. **数据抓取层**：超长窗口分页拉取应加重试 / 退避；对抓取失败的股票不应静默丢弃，
   应在结果里明确提示"N 只拉取失败"，并优先命中本地缓存减少重复网络请求。
2. **计算层**：
   - 对"候选池大小 × hist"设合理上限或分块处理，避免单次样本量爆炸；
   - 超参寻优的 trial 数应可配置并给出耗时预估；
   - ML 回测的 Walk-Forward 训练应丢到线程池执行，避免阻塞事件循环。
3. **隐藏放大**：时间段自动抬升 `hist` 时给出明确提示，并对自动抬升设天花板，
   避免用户无感知地放大到不可行区间。

## 6. 结论

"时间长度过长跑不出结果"不是单一 bug，而是**长窗口下的数据抓取失败 + 计算量膨胀 + 时间段自动撑大 hist**
三者叠加的系统性表现：要么因上游 K 线超时、整池样本拉不到而直接报错，
要么因样本量 / 重训次数爆炸、甚至回测阻塞后端而长期无响应。
